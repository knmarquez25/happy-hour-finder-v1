# New-place discovery and owner review

Approved behavior: keep all recorded menus visible; accept a natural-language happy-hour request; discover additional LA/Orange County places outside the researched list; show them under Needs verification. Include an item without a published price only when happy-hour evidence supports it; label Price needs confirmation. Visitors can supply evidence; only Kathy approves publication. Missing service access must show a truthful error, never substitute invented places or call an existing dataset result a new discovery. No paid plan, billing enablement, or paid fallback.

Implementation choices: preserve vanilla frontend, GitHub Pages, Render Node server. Use Gemini 2.5 Flash-Lite Google Search grounding only if the existing free project permits it; Gemini 3.5 Flash-Lite extracts bounded structured candidates from cited search passages. Return only candidates supported by a cited passage and mark all as unverified. No arbitrary server URL fetching. Dedupe existing names/locations and stable candidate identities. Respect Google search attribution through a sandboxed search-entry iframe plus citation links.

Supabase Free stores candidate payloads, immutable original discovery evidence, community evidence, approval status, reviewer ID/date. Only server service-role credentials write; direct anon/auth table writes denied by RLS. Owner signs in with Supabase Auth; server validates token with Auth and compares configured owner UUID before approve/reject. Public input cannot choose status/reviewer fields. Approval snapshot is immutable to public evidence submissions; new evidence never edits an approved listing. Owner reviews/editable offer fields before approval. Public notes/evidence contain only menu information and source links, no names/contact details. No photo uploads in first version: public photo/post URLs can be evidence.

Approved additions join the browsable main list, with owner-review date rather than a claim of live restaurant confirmation. Existing deterministic pricing and menu selection remain unchanged. Pending records never enter confirmed results or budget combos. Unknown prices remain null. A pending candidate may be saved only once per stable name/location key. Community evidence is source URL plus short text, bounded and rate limited, without counts labeled as verification.

Configuration required: SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, OWNER_USER_ID, SEARCH_MODEL=gemini-2.5-flash-lite. Owner manually creates Auth user and enters secrets privately. App degrades to browsing when unavailable; deployment is not complete until a real new-place search and owner-only approval persistence work publicly.

Deployment ruling (October 26): the actual Gemini 2.5 grounded search call was rejected. Replace that search stage with Tavily Basic (auto_parameters=false, twelve source results, one credit/request), using its Free no-card account. Existing Gemini 3.5 performs structured extraction from literal returned source excerpts. TAVILY_API_KEY is private in Render. No provider is silently switched or upgraded on quota failure. Supabase tables and owner Auth user are created. Its service role and public/anon keys were privately saved by the user into Render; live queue GET returned 200 and unsigned owner GET returned 401.

Evidence ruling: extraction returns source/fragment indices rather than retyped URLs/quotes. Server copies the exact title and selected literal fragment into separately labeled evidence lines. Happy hour must be explicit in that page title or selected fragment, and item names must occur in the retained fragment. Venue/location can be elsewhere in the same source context. A price must follow its own item directly in that retained fragment; otherwise it remains unknown. Owner review is still required for scope, current offers, and conditional pricing.
