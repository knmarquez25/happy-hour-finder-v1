# AI-guided menu discovery

Date: 2026-10-25

## Intent and approval

The user approved a menu-first browse view with an always-visible AI helper, one natural-language request box, no preference dropdowns, and a single results list. First load includes all 111 researched restaurants; no location, time, budget, or food is silently required. Clear request restores the complete dataset. Users may specify area, food, drinks, budget, or a combination. Initial combinations are suggestions; users browse menus and select items themselves. Source evidence and unknown prices remain explicit.

## Scope and builder choices

Keep the existing plain JavaScript dataset, matching helpers, and source provenance. Replace the primary index with the approved interface, preserving the existing interface at `legacy.html` for comparison and historical browser checks. No restaurant facts or prices are generated by the model. AI extracts optional preferences using OpenAI Responses structured outputs; deterministic code searches the reviewed dataset and calculates money in cents. Every request replaces previous preferences; no hidden conversation memory. Day/time can be included in prose; unspecified timing means browsing listed offers, never a claim that happy hour is currently active.

Builder choice: a dependency-free Node 22 server serves public assets and `/api/discover`, with an environment-only `OPENAI_API_KEY` and configurable `OPENAI_MODEL` (default `gpt-4.1-mini`). Render is the recommended hosting option, with no account creation, paid commitment, public deployment, or paid API calls during implementation. Static hosting still supports browsing; the helper honestly explains when its server is unavailable. No keyword parser pretends to be AI. Live model evaluation and publication require deployment/account configuration and must be reported pending if unavailable.

This iteration searches the curated dataset. It does not crawl TikTok, retrieve live menus, or verify current restaurant offers. The interface and write-up explain that boundary. Future source retrieval is separate work, not an implied capability.

## Workflow and decision space

1. Research workflow: source discovery → AI-assisted extraction → human review of item, price, schedule, restrictions, and attribution → dataset validation → versioned publication. No source is auto-promoted to verified.
2. On entry, browse all restaurant records with their location, listed schedule, menu highlights, prices/unknowns, source review dates, and menu links. Dataset inclusion is different from a time-qualified recommendation.
3. A user enters up to 1,000 characters; on submission, text goes to the app server and OpenAI. Show a concise privacy notice before the submit button.
4. The model returns area, food/drink preferences, flexible budget, atmosphere, optional day/time, and clarification. The server rejects malformed/unknown fields, unsupported areas, refusals, incomplete output, and invalid time/budget. No model-provided prices, restaurant identifiers, URLs, or HTML are accepted.
5. Show the interpreted request next to the single result list. Area and explicit food/drink requirements narrow results. Budget ranks suggestions and labels overages without excluding venues. Missing price information stays unknown. If the request needs clarification, leave the previous list visible and explain the issue.
6. Offer menu-supported combos with a shared primary-evidenced schedule; show the relevant seating restrictions and offer window. Without a full day/time request, show listed schedules rather than implying now. If only a day or only a time is supplied, filter against evidenced compatible windows without defaulting the other field.
7. User expands the menu and selects one published order of each item. Recalculate the displayed menu-price subtotal, label any unknowns or unconfirmed prices, and flag selections lacking a shared supported schedule or valid pairing. Arithmetic never certifies availability or allergy safety.
8. Clear request aborts in-flight requests and resets preferences/results; stale responses never overwrite newer browsing state. API failures leave browsing usable.

Human decisions: what to ask, correcting interpretation, comparing sources, choosing items and restaurant, confirming uncertain offers, approving research records, and configuring/publishing the hosted app. No ordering, booking, messaging, or location permission is performed.

## Guardrails and constraints

- API keys stay on the server. Static serving uses an explicit public path allowlist and does not follow symlinks outside it.
- Server validates same-origin browser requests, bounded bodies, timeouts, per-address/global rate limits, and concurrent calls. No request logging or persistent query storage. `store: false` on AI calls is not a promise of zero provider retention.
- In-memory limits are suitable for a small class demo, not distributed abuse prevention. Production needs gateway controls and account usage limits.
- Render only escaped dataset/model text and HTTP(S) source links; external links use `rel="noreferrer"`.
- Primary/secondary/conflicting/unknown evidence remains differentiated. Dates are source-review dates, not live availability checks.
- Preserve the historical engine and unchanged 15-case / five-case holdout evaluation. New tests and evaluations must not be called live model accuracy or a human usability study.
